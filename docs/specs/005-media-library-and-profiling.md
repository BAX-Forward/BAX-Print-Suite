# Spec 005: Media library, output modes and color profiling (Milestone M6, extension M6b)

Target repo: **github.com/BAX-Forward/BAX-Print-Suite**. Read `docs/ARCHITECTURE.md` (§3.3 ColorEngine and PrinterDriver, §3.8 capability profiles, §4 `Media` and `Profile`) and Spec 001 first.

## Clean-room rule (read first)
Same as Spec 001. Build from this spec, ICC.1:2022 (ICC v4) and ICC.2 (iccMAX, read-only awareness), ISO 12647/ISO 13655 (measurement conditions), ANSI CGATS.17 (measurement data exchange format), ISO 17972 (CxF/X), and the public docs of LittleCMS. Don't model the workflow, screens, categories or option names on any commercial RIP. No commercial product names. Vendor media catalogs arrive only through vendor plugins (ADR-0005).

## Goal
1. `packages/media`: a vendor-neutral **media library**: media records, the **output modes** a device offers for each medium, and the color setup attached to each (medium, mode) pair.
2. A **profiling workflow** in `apps/server` that takes a (medium, mode) pair from "uncharacterized" to "verified" in resumable steps: print a target, read measurements, compute calibration and an output ICC profile, verify, and publish a revision.
3. **Revisioned color setups** so every job records exactly which calibration and profile it was rendered with (Spec 008 depends on this for faithful reprints).

## User stories
- As an operator, I add a new roll of material, clone the setup from a similar medium, and print with it today, then refine it later.
- As a color technician, I characterize a medium on a device in steps I can pause and resume, using whatever spectrophotometer I own or a measurement file from another tool.
- As a production manager, I want reprints six months from now to use the same calibration as the original job, even if the profile was updated since.
- As a shop with several identical printers, I export a medium's setup from one machine and import it on another.

## Concepts and our own terms
| Term | Meaning |
|---|---|
| `Medium` | A substrate as the shop knows it: name, kind (free-text tag plus an optional controlled vocabulary such as `film`, `paper`, `textile`, `rigid`, `adhesive`), width(s), thickness, roll or sheet, one- or two-sided |
| `OutputMode` | A device-declared way of printing: resolution, pass count, ink set, direction, plus any opaque plugin parameters. Comes from the PrinterDriver capability profile. Core never interprets the opaque part |
| `ColorSetup` | Per (medium, mode): characterization **level**, linearization curves, ink limits, output ICC profile ref, rendering-intent default |
| `ColorSetupRevision` | Immutable snapshot of a `ColorSetup`. Jobs reference revisions, never the mutable head |
| `Preset` | A named bundle: medium + mode + color setup + rendering intent, selectable per hot folder or per job |

### Characterization levels
Three levels, because each adds one independent physical correction on top of the previous one:
- **L1 – profile only:** an output ICC profile is assigned (generic or built elsewhere). Cheapest; good enough when the device behaves like the profile's source.
- **L2 – linearized:** per-channel 1-D tone curves bring each colorant to a target response (e.g. ΔE-from-paper or density-based), plus a **total area coverage (TAC) limit**, then a profile is built on the linearized device.
- **L3 – channel-limited:** adds a per-channel maximum before linearization, to stop individual colorants from over-inking (bleed, cockling, drying problems) independent of the total.

## Functional requirements
- **FR1 Library CRUD:** create, clone, rename, archive and delete media. Deleting a medium referenced by any job is refused; archiving hides it from pickers but keeps it resolvable.
- **FR2 Modes from devices:** `PrinterDriver/1.listMedia()` is extended (minor version, optional) with `listModes(mediumHint?)` returning `OutputMode[]` with a stable `modeKey`. Core stores what the device reports and lets the user hide modes; it never invents modes.
- **FR3 Device sync:** a "refresh from device" action merges device-reported media and modes. Merge rule: device-provided fields update; any `ColorSetup` the user has edited (has ≥1 user revision) is never overwritten. Conflicts are listed for the user to resolve.
- **FR4 Profiling workflow** (`/profiling-sessions`), a state machine `created → target_printed → measured → computed → verified → published` (plus `abandoned`). Each step persists its inputs/outputs as job-step artifacts, so a session survives restarts and can be resumed from any completed step.
  - **Targets:** generated by us as PDF (ISO 32000) patch charts with a CGATS.17 layout file describing patch ids and nominal device values. Patch set sizes are chosen per level (single-channel ramps for L2/L3, a multi-dimensional set for profile building). Default ramp: 21 steps per channel (5 % increments); 5 % is below the step at which most viewers see banding in a ramp and keeps the chart to one strip per channel.
  - **Measurements:** from a `Spectro` plugin (new optional plugin interface `Measurement/1`: `listInstruments()`, `measureStrip(layout)`), or by importing CGATS.17 or CxF/X files. Measurement conditions (M0/M1/M2, ISO 13655) are recorded and must match across a session; mismatch is an error.
  - **Compute:** linearization and limits in core (pure TypeScript); profile building via the `ColorEngine` plugin's new optional `buildProfile(measurements, opts)`. An external, user-installed profiler (e.g. an AGPL tool) may be wired as a separate-process plugin per ADR-0004; it is never required.
  - **Verify:** print a verification chart, measure, report ΔE2000 per patch (mean, 95th percentile, max). Default pass threshold: mean ΔE2000 ≤ 2.0 and 95th percentile ≤ 4.0, in line with commonly used ISO 12647-based proofing tolerances. Thresholds are per-preset settings.
  - **Publish:** creates a new `ColorSetupRevision` and moves the head.
- **FR5 Limits:** TAC limit expressed in percent of a single full channel (e.g. 300 = three channels at 100 %). There is no global default value: the workflow derives a proposed TAC from the measured L2 data as the coverage at which the next 10 % adds less than ΔE 1 in lightness, and shows it as a proposal the user accepts.
- **FR6 Revisions:** every edit produces a revision with author, timestamp, reason, and content hash. `Job` records `colorSetupRevisionId` at the render step.
- **FR7 Presets:** named presets selectable per hot folder (Spec 001 `HotFolder.ticketTemplate`) and per job (Spec 007 editor).
- **FR8 Exchange format (ours):** `.bpsmedia` = zip containing `medium.json` (JSON Schema published in `packages/media/schema`), referenced ICC profiles, curves as CGATS-like text, and a manifest with SHA-256 of each member. Profiles carry `provenance` (ARCHITECTURE §4); non-redistributable profiles are omitted on export with a warning.

## Acceptance tests
1. **Unit (Vitest):**
   - Cloning a medium deep-copies the color setup head but starts a fresh revision chain referencing its origin.
   - Deleting a medium referenced by a job throws `MediumInUseError`.
   - Device sync over a fixture with 3 modes, one of which has a user revision, updates the other two and leaves the edited one byte-identical.
   - Profiling-session transitions: exhaustive table test; illegal transitions rejected with a typed error; resume after a simulated restart continues from the last persisted step.
   - CGATS.17 parser round-trips our fixture files; rejects files with missing `NUMBER_OF_SETS` or mismatched field counts.
   - Linearization: given a synthetic measured ramp produced by a known gamma curve, the computed correction composed with the device curve is monotonic and within 1 % of the target response at every step.
   - TAC proposal on a synthetic saturating dataset equals the analytically expected coverage ± 5 %.
2. **Differential (own fixtures):** run a full session against a **simulated device** (a LittleCMS transform from a known ICC profile, plus deterministic noise) and assert the verification ΔE2000 mean ≤ 1.0 against that ground truth. Rerun with the external-profiler plugin when installed and compare both outputs on the same patches (report only; tolerances in `test/thresholds.json`).
3. **Exchange:** export then import `.bpsmedia` round-trips (hash-equal JSON); a non-redistributable profile is excluded and the import reports the missing ref.
4. **Integration (after 001):** a job rendered with preset P stores `colorSetupRevisionId`; publishing a new revision later doesn't change the stored id.
5. Lint, license check, vendor-neutral check pass (no vendor or model names in `packages/media`).

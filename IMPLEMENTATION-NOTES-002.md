# Implementation notes: Spec 002 (dashboard shell on a mocked API)

Scope of this change: **Part B of `docs/specs/002-dashboard-and-rip-handoff.md`**, the operator
dashboard in `apps/dashboard` (React 18 + Vite + TypeScript, per ADR-0006). It runs against an
MSW mock of the HTTP API that Spec 001 provides and Spec 002 Part A extends. The server, the handoff
plugin and auto-dispatch are not part of this change.

## What was built

### Mock API (`apps/dashboard/mock/`)
- `openapi.json`: the API contract the UI codes against, made of the Spec 001 endpoints plus the
  Part A additions: `/health`, `/openapi.json`, `GET /jobs` (with `status`, `q`, `hotFolderId`,
  `deviceId`, `sort`, cursor paging `{items, nextCursor}`), `GET/PATCH /jobs/{id}`,
  `GET /jobs/{id}/transitions`, `GET /jobs/{id}/file`, `GET /jobs/{id}/preview` (reserved and
  answers `501 {reason:"no-render-engine"}`), `POST /jobs/{id}/print`, `GET/POST /hotfolders`,
  `PATCH/DELETE /hotfolders/{id}`, `GET /plugins` (with `configSchema` and the PrinterDriver/1.1
  `accepts`/`documentTypes` capabilities), `GET/POST /devices`, `PATCH /devices/{id}`, and `GET /events`
  (SSE, CloudEvents). Errors use `application/problem+json` with per-field `errors`.
- `db.ts`, `transitions.ts`, `fixtures.ts`, `pdf.ts`: an in-memory store with 14 fixture jobs,
  a transition table, validation (paths, priorities, device config against the plugin schema),
  simulated pipeline steps, simulated handoff delivery (`deliveredPath`, audit `delivery` record),
  and generated PDFs, including a 3-page fixture for thumbnails. No files are read or written.
- `handlers.ts`: MSW handlers for every operation. `events.ts`: an event bus plus a mock
  `EventSource`. `browser.ts`: starts the mock in the browser for `dev:mock`, and a sample file
  "arrives" every 45 s so live updates are visible.

### Dashboard (`apps/dashboard/src/`)
- `api/`: `schema.ts` is generated by `openapi-typescript`. `client.ts` is the only module allowed
  to call `fetch`. `queries.ts` holds the TanStack Query hooks.
- Screens: **Jobs** (all spec columns, multi-status/hot folder/device/text filters kept in the URL,
  column sorting with `aria-sort`, cursor "load more", virtualized rows past 200 items, live SSE
  updates, bulk hold/queue/cancel/priority), **Job detail** (metadata, page list with size and trim
  box, lazy "Screen preview" thumbnails, the step and audit timeline, the error panel, actions
  enabled only from `GET /transitions`, priority 0–100, send to device, mark done), **Hot folders**
  (list, add with all options, inline server path errors, enable/disable, remove with confirmation),
  and **Devices** (list, auto-dispatch toggle, add device with a config form generated from the
  plugin's JSON Schema, inline server field errors, offline status with reason).
- Previews (`preview/`): the UI tries `GET /preview` first and, after the 501, renders with
  pdf.js in a Web Worker (OffscreenCanvas). If that isn't available it falls back to the main
  thread. Thumbnails are capped at 320 px and the file is loaded once per job.
- Global: SSE connection indicator with reconnects, toasts (errors as alerts, successes as
  polite status messages), a skip link and landmarks, keyboard navigation, an in/mm toggle,
  and all en-US strings in `strings.ts`.
- Lint rule (`eslint.config.js`): `fetch`, `window/globalThis/self.fetch` and `XMLHttpRequest`
  are forbidden outside `src/api/client.ts`.

### Tests
- Vitest (`apps/dashboard/tests/`), jsdom plus MSW in Node:
  - `contract.test.ts`: calls every operation, produces every documented status code and checks
    each JSON body with Ajv against `openapi.json`. It fails if an operation or status goes untested.
  - `jobs-page`, `job-detail`, `hotfolders-page`, `devices-page` and `shell` tests cover each
    screen requirement in Part B (the test names follow the spec wording).
  - `lib.test.ts` covers formatting, URL filters, the timeline, CloudEvents parsing, the SSE client,
    cache patching and the thumbnail pipeline fallbacks.
  - `no-direct-fetch.test.ts` runs ESLint to prove the fetch rule works and that `src/` is clean.
- Playwright (`apps/dashboard/e2e/mock-smoke.spec.ts`, Chromium, mock mode): the acceptance 7
  smoke test (jobs list, filters, search, live connection, non-blank pdf.js thumbnail, inline
  hot-folder path error) and the acceptance 8 axe check (no serious or critical violations on Jobs,
  Job detail and Hot folders).

## Commands

```sh
pnpm install
pnpm --filter dashboard dev:mock        # UI on MSW at http://127.0.0.1:5173/ui/
pnpm --filter dashboard test            # Vitest (unit, screens, contract, lint rule)
pnpm --filter dashboard lint
pnpm --filter dashboard typecheck
pnpm --filter dashboard build           # assets in apps/dashboard/dist
pnpm --filter dashboard exec playwright install chromium
pnpm --filter dashboard e2e:mock        # Playwright smoke + axe in mock mode
pnpm --filter dashboard gen:api         # regenerate src/api/schema.ts from mock/openapi.json
```

`pnpm --filter dashboard dev` (without mock) proxies API paths to `http://127.0.0.1:8080`, or to
`BPS_API_URL` if set. `public/mockServiceWorker.js` is generated by `msw init` and is git-ignored.

Dependency versions are pinned in `apps/dashboard/package.json`. No lockfile is committed.

## Deferred (out of this change's scope)
- **Part A (server):** the real endpoints in `apps/server`, serving `dist` at `/ui`, and the
  server's contract tests. When the server lands, its `/openapi.json` should replace
  `mock/openapi.json` (or be diffed against it), followed by `gen:api`.
- **Part C:** the `plugins/printer-handoff` plugin, the PrinterDriver/1.1 additions to `plugin-sdk`
  (`accepts`, `submitDocument`, `configSchema`), and the conformance kit. The mock only simulates
  delivery results.
- **Auto-dispatch scheduler** and the device status polling on the server.
- **Acceptance:** 1 (server `/ui`, CI matrix), 3–5 (plugin, scheduler, integration), 6 (full
  Playwright suite against a real server with temp dirs), and 9 (repo license check, owned by
  Spec 001 CI). Acceptance 2 is covered for the mock contract only, and 7–8 are covered in mock mode.

## Notes for reviewers
- Core code contains no vendor, model or commercial RIP names. Fixtures use generic device names
  ("Roll A") and neutral paths (`/srv/print/hot/...`, `/srv/rip/in/...`). Device profiles for the
  priority hardware belong in `plugins/` and capability profiles, not here.
- Commits need a DCO sign-off (`git commit -s`), per `CONTRIBUTING.md` and ADR-0002.
